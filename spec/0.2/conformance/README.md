# Conformance corpus of Carve 0.2

One corpus for every engine. Three plain JSON files, one schema (`schema.json`, JSON Schema 2020-12). Each file has `$schema`, `kind` and `description`, and one list. A fourth file, `extensions.json`, holds the standard extension corpus (see "Extensions"); it is outside the schema and is part of the readiness gate.

| File | `kind` | List | Made by |
|---|---|---|---|
| `examples.json` | `examples` | `examples`: every example of the ten documents | generated by `scripts/spec2-conformance.mjs --write`; do not edit |
| `clause-cases.json` | `clause-cases` | `cases`: inputs a clause decides that no example holds | curated by hand |
| `refused-trees.json` | `refused-trees` | `trees`: trees a 2.0 reader refuses | generated from `trees/refused.json`; do not edit |

`npm run spec2:data` runs `node scripts/spec2-conformance.mjs --check`, which fails when a generated file is stale, when a file does not match the schema, when a clause case cites a clause no document defines, when its `why` is not text of the clause it names, when its expected children are not a valid tree, and when it repeats the input and options of an example.

## Examples

Each entry:

| Field | Value |
|---|---|
| `id` | the document stem and the example number, as `syntax-blocks-12` |
| `document`, `number` | the document file and the number the example has there |
| `section`, `clauses`, `clauseScope` | the heading of the section the example stands in; the clause ids the heading of the example names after its status, as `Example 9 (unverified, C2-W-037, C2-W-038)`, with `clauseScope` `example`, or else the clause ids that section defines, with `clauseScope` `section`. A section list is no claim that the example exercises each of its clauses. |
| `kind` | `render`: Carve input to HTML; `write`: Carve input to canonical Carve; `lint`: Carve input to the codes lint reports; `include`: an entry document and the files a resolver serves; `import`: HTML input to a tree and canonical Carve |
| `input` | the Carve input; absent for `import` |
| `html` | the HTML input of an `import` example |
| `files` | for `include`: each file the resolver serves under its name, which is also its id, as `{ "text": ... }` or as `{ "bytes": "61 FF" }` in hex |
| `options` | the options the example's flags set, by the names of `data/options.json` (see "Options"); `{}` for none |
| `expected.html` | the expected HTML |
| `expected.htmlIncludes` | where the example states its output in prose: a piece the HTML holds |
| `expected.tree` | the expected tree, positions included, where the tree gate holds one (`trees/`) |
| `expected.children` | for `import`: the children of the imported document, without positions |
| `expected.carve` | for `write` and `import`: the source the canonical writer gives, with its final line feed (C2-W-022) |
| `expected.diagnostics` | the codes of `data/lint-rules.json` on the line of the example that starts with `Reported:`; no code is taken from other prose. Not a complete list, except for `lint`, where it is what the example states |
| `status`, `reason` | `verified` or `unverified`, and why, as the conventions of the document define it |
| `note` | where the example states its input in prose (blocks Example 247) |

Comparing: HTML is compared byte for byte, and so is Carve source (`expected.carve`). A tree is compared under the equality of C2-A-162, or with positions where the engine claims C2-A-165. An include example is parsed with a resolver that serves exactly `files` and returns each name as its id (`includes.md`, conventions).

What the status means:

- `syntax-blocks`, `syntax-inline`, `html`, `writer`: *verified* is what the documents call *generated*, the output of the 0.1 reference engine for an input whose 0.2 rule equals 0.1 behavior; *unverified* output is written by hand from the clauses.
- `includes`: every example is unverified (`includes.md`, conventions). Its tree in `expected.tree` comes from the tree gate.
- `import-html`: *verified* means the reference importer at the commit the conventions name gives this tree and source.

An unverified example is still the expected result: where an engine differs, the clause decides.

## Clause cases

Each entry has `id` (`CC-nnn`), `clauses`, `why`, `summary`, `options`, `expected` and `from`, the engine case files it was merged from (`js:ID`, `php:ID`, `rs:ID`; empty for a case written from the clauses). `why` quotes the sentence that decides the case, as `C2-B-130: ...`; several quotes follow one another, and ` ... ` joins two pieces of one clause. A catalog trigger may be quoted as `Catalog rule-id: reports fragment`; the gate checks it against that row. `corrected`, where present, says what the engine files expected before the clause corrected it. `engineLocal`, where present, names an implementation choice that a clause leaves open and on which `expected` depends, as C2-W-133 leaves open which groups need a repair parse: the expectation holds for an engine that made that choice, and another engine may differ without failing the case. The readiness gate still replays such a case and counts an outcome other than a pass as engine-local, never as a gap or a regression (`scripts/next2-readiness.md`).

`kind` names the call the case runs (`tooling.md`, C2-T-005). An entry without `kind` is a render whose `expected` states both `html` and `children`, the children of the document without positions; that is the shape of every case up to CC-359.

| `kind` | Input | Call | What `expected` may state |
|---|---|---|---|
| `render` | `input` or `inputBytes`, `files`; or `tree` | `renderWithDiagnostics`, and `parse` for `children` | `html`, `children`, diagnostics, `refusal` |
| `parse` | `input` or `inputBytes`, `files` | `parseWithDiagnostics` | `children`, `tree`, diagnostics, `refusal` |
| `lint` | `input` or `inputBytes`, `files` | `lint` | diagnostics, `refusal` |
| `format` | `input` or `inputBytes` | `formatWithDiagnostics` | `carve`, diagnostics, `refusal` |
| `layout` | `input` or `inputBytes` | `parseWithLayout` | `layout`, `layoutAbsent`, `children`, diagnostics |
| `write` | `tree`, and `layout`, its sidecar | `writeWithDiagnostics`, and `write` for a refusal | `carve`, diagnostics (the losses), `refusal` |
| `tree` | `tree`, a JSON value, or `json`, JSON text | `decodeTree` with `options.extensions` registered | `accepted`, `tree`, `refusal` |
| `migrate` | `tree`, a 1.x or draft tree | `migrateTree` | `tree`, diagnostics, `refusal` |
| `import` | `html` | `importDocument` with `from: "html"` | `children`, `carve`, diagnostics, `refusal` |
| `cli` | `args`, `stdin`, `files` | the program `carve` | `status`, `stdout`, `stdoutJson`, `stdoutDiagnostics`, `stderrCategory`, `stderrDiagnostics`, `filesAfter` |
| `position` | `input` or `inputBytes`, `offset` | `positionOf` | `line`, `column`, `refusal` |
| `diff` | `input` and `inputAfter`, both parsed with positions off | `diffTree`, then `applyPatch` | `applies`: the patch applied to the first tree gives the second; `patch` only where C2-T-043 fixes it, the empty list for two equal trees |
| `patch` | `input`, parsed with positions off, `patch`, and `fingerprintOf`, a source whose tree gives the `fingerprint` | `applyPatch` | `children`, `refusal` |
| `fingerprint` | `input` or `inputBytes`; `of: "tree"` hashes its tree parsed with positions off | `sourceFingerprint`, or `treeFingerprint` | `fingerprint` |
| `export` | `input`, and `to`: `markdown`, `plain` or `ansi` | the export of `to` (C2-T-003) on the tree of `parse(input)` | `output`, the exported text; diagnostics, `refusal` |

`inputBytes` is the input as bytes in hex, for a source that is not well-formed UTF-8 (C2-B-218). `files` holds the files a resolver serves, as for an include example; a case with `files` is parsed with that resolver and one without `files` with none (see "Options"). A file entry with `{"error":"outside_root"}` or `{"error":"unreadable"}` makes the resolver return that cause for the path, so include failure cases do not depend on filesystem permissions or the runner's directory.

`expected.children` and `expected.tree` are compared field by field, unlike the tree equality of C2-A-162: the resolution fields of `data/ast-results.json` count too, so a case pins a field such as `abbreviation.expansion` by stating it and pins its absence by leaving it out. Only `pos` and `segments` are skipped where the expected value holds no `pos`, `srcByteLength` where it states none, and the `children` and `file` of an `include`.

### Diagnostics

`expected.diagnostics` lists entries of the record the call returns. An entry is a code, or an object with `code` and any of `line`, `column`, `endLine`, `endColumn`, `severity`, `channel`, `path` and `file`. `line` and `column` are the start of the entry's `range`, counted as `pos` counts them (C2-A-141): lines from 1 at each line feed, columns in code points from 1. They are counted in the file the entry names (`file`, C2-N-063) and in the input otherwise; the end is exclusive, as in `pos`. A field the object does not state is not compared. `messageWhen`, when present, is the exact `when` text of the selected message variant in `data/lint-rules.json`; the runner compares that variant, and the corpus check verifies that the row lists it.

`expected.diagnosticsComplete` set to `true` says the record holds the listed entries and no others; otherwise it holds at least them, in any order. `expected.notReported` lists codes the record must not hold: the near miss of a rule. `expected.suppressed` is the `suppressedDiagnostics` of the result (C2-T-024).

```json
{
  "kind": "lint",
  "input": "a **b** c\n",
  "options": {},
  "expected": {
    "diagnostics": [{ "code": "markdown-strong-double-star", "line": 1, "column": 3, "endLine": 1, "endColumn": 8, "channel": "lint" }],
    "notReported": ["markdown-strikethrough-double-tilde"]
  }
}
```

The check fails a code that `data/lint-rules.json` does not list or lists as obsolete or void, a `channel` or `severity` that differs from the catalog, a position outside the text it is counted in, and a code that is both expected and excluded.

### Layout and writing

A `tree` case may give `annotations` beside its tree. The reader checks the supplied annotation-range sidecar under C2-A-203, C2-A-207 and C2-A-214; without it, only the tree checks run.

A `layout` case compares the sidecar that `parseWithLayout` returns with `expected.layout`. Each root field the expected sidecar states is equal, and each node entry it states is an entry of the result with the same `path`, compared as C2-L-059 says: a required fact must be present and equal, and an optional fact the case states is compared only where the result records it. The result may hold more entries and more facts; `expected.layoutAbsent` names, for a path, the facts its entry must not hold. A `write` case gives the writer a `tree` and, where it has one, the sidecar `layout`, and compares the source with `expected.carve` and the losses of the record with `expected.diagnostics`.

```json
{
  "kind": "layout",
  "input": "> a\n",
  "options": {},
  "expected": {
    "layout": { "lineEndings": "lf", "nodes": [{ "path": "/children/0", "startByte": 0, "endByte": 3, "fenced": false }] },
    "layoutAbsent": { "/children/0": ["openerRaw"] }
  }
}
```

```json
{
  "kind": "write",
  "tree": { "type": "document", "astVersion": "2.0", "children": [{ "type": "block_quote", "children": [{ "type": "paragraph", "children": [{ "type": "text", "value": "a" }] }] }] },
  "layout": { "version": 2, "encoding": "utf-8", "source": "::: >\na\n:::\n", "lineEndings": "lf", "bom": false, "nodes": [{ "path": "/children/0", "startByte": 0, "endByte": 11, "fenced": true }] },
  "options": {},
  "expected": { "carve": "::: >\na\n:::\n" }
}
```

The check fails a sidecar the layout schema refuses (a supplied one, unless the case expects `CarveLayoutError`), an expected sidecar whose `source` is not the input or whose ranges lie outside it, and a fact both expected and excluded.

### Command lines

A `cli` case runs the program (`tooling.md`, C2-T-002) with `args`, the arguments after the program name, in a directory that holds exactly `files`, with `stdin` on standard input (empty where absent). Its `options` are `{}`: a command line sets options with flags. `expected.status` is the exit status and is always stated. `stdout` is standard output byte for byte, and `stdoutJson` the same output read as one JSON document and compared as a JSON value (C2-T-023). `stdoutDiagnostics` and `stderrDiagnostics` are the diagnostic lines of C2-T-019 on each stream, in order, as diagnostic objects whose `file` is the FILE of the line; the message is not compared, and a line carries no `channel`. `stderrCategory` is the CATEGORY of the failure line `carve[CATEGORY]:` that opens standard error (C2-T-039), and `null` where standard error holds no failure line. `filesAfter` gives files of the directory after the run: `{ "text": ... }`, `{ "json": ... }` for a report compared as a JSON value, or `null` for a file that must not exist.

```json
{
  "kind": "cli",
  "args": ["fmt", "--check", "a.crv"],
  "files": { "a.crv": { "text": "a\n\n\nb\n" } },
  "options": {},
  "expected": { "status": 1, "stdout": "a.crv:3\n- \n+ b\n", "stderrCategory": null }
}
```

The check fails a command or a flag that `data/cli.json` does not list for the command, unless the case expects the category `usage`; a category whose status differs from the one `data/cli.json` gives it; and a field of a command line expected from a library call, or the other way round.

### Positions

A `position` case calls `positionOf` (C2-T-041) with the input and `offset`, a UTF-8 byte offset into it, and compares `expected.line` and `expected.column` with the result, or expects the refusal `CarveOptionError` with the path `/offset`. Its `options` are `{}`.

```json
{
  "kind": "position",
  "input": "a\nbé c",
  "offset": 6,
  "options": {},
  "expected": { "line": 2, "column": 4 }
}
```

The check fails `line`, `column` or `offset` on a case of another kind, and a position case that sets options or expects anything else.

### Refusals

`expected.refusal` says that the call throws: `error`, the typed error of the table of C2-T-040 (`tooling.md`), and `path`, the RFC 6901 pointer of what the error names, into the tree, the sidecar or the options the call was given (C2-A-167). An error that names the node at `path` or a field below it agrees. A refusal stands alone in `expected`, except for the diagnostics a `CarveWriteError` carries (C2-W-134). `expected.accepted` says that the reader accepts the input, and `expected.tree` gives the tree the call returns, compared under C2-A-161 and with positions where the case states them.

```json
{
  "kind": "render",
  "input": "a",
  "options": { "headingIds": "upper" },
  "expected": { "refusal": { "error": "CarveOptionError", "path": "/headingIds" } }
}
```

The check fails an error that no category of `data/cli.json` names or that the call of the case does not throw. A case whose `tree` is not refused must hold a tree the schema and the reader checks of `scripts/lib/spec2-reader.mjs` accept; one that expects `CarveTreeError` for a `tree` must hold a tree one of them refuses, at `path` where a reader check refuses it.

## Options

`options` takes every option of `data/options.json` by its name, and `{}` is every default. The check fails a value that the row of the option does not allow, except a value the case expects to be refused (`expected.refusal` with `CarveOptionError` and the path of that option). Three options take host code, which JSON cannot hold, so a case names it: `extensions` lists standard extensions by their names in `data/extensions.json`, also for `decodeTree` and `validateTree`, and `renderers` maps such a name to `"standard"`, its standard renderer, which under the `mode` `static` is its build-time renderer (C2-X-052), or to `{ "standard": { ... } }`, that renderer created with the host options in the inner object, which the `rendererOptions` of its row in `data/extensions.json` name: `{ "carve.tabs": { "standard": { "mode": "aria" } } }` is the tabs renderer in `aria` mode (C2-X-056). The top-level `mode` stays the render option of C2-H-122. `codeBlockRenderer` (C2-H-206) is an object that the runner turns into a function: for a code block whose `syntax` is the field `syntax`, or for every code block where the field is absent, the function returns `result`, and for every other block it returns nothing. A string `result` is a template in which `{default}` stands for the default HTML and `{syntax}` for the language of the block, or the empty string where it has none, both replaced in one pass over the template; `null` returns nothing, and a number returns that number, a value that is not text. That object is a spelling of the corpus only, not an interface: an engine offers `codeBlockRenderer` as a function of its language, and a binding that crosses a JSON boundary passes a callback across it, not this object. `allowLosses` lists codes of the render-loss channel, `maxLosses` is a count, and `headingShift` a count up to the `maximum` of its row. `includes` holds `file`, the id of the top-level document, and the lowered limits `depth` and `bytes`; a case with `files` is parsed with a resolver over them, and a case without `files` with no resolver. `rules` maps a code to `on` or `off`, and `platforms` lists platform names.

```json
{ "rules": { "djot-plus-bullet": "on", "bare-html-tag": "off" }, "platforms": ["github"], "extensions": ["carve.tabs"], "renderers": { "carve.tabs": "standard" } }
```

## Extensions

`extensions.json` (`kind` `extensions`, list `cases`) checks the HTML of the standard extensions. Each extension has cases for its default use, its host options, a use inside a list item and inside a block quote, literal code text, and escaped user text, with its fallback where no renderer is selected. An entry has `id` (`EXT-nnn`), `extension`, `summary`, `clauses`, `expectedFrom`, `kind` (`render`), `input`, `options` and `expected` (`html`, `htmlIncludes`, diagnostics), read as in a clause case.

`expectedFrom` says where the expected HTML comes from. `0.2` means the 0.2 clauses in `clauses` decide it. `0.1: ...` names the documented 0.1 output it follows, a row of `tests/corpus-optional` or an extension page, where 0.2 has no text for the renderer yet; `clauses` then lists only the 0.2 clauses the case also relies on, such as C2-H-047 for literal code text. No expectation is copied from an engine. Where the engines agree on a detail that neither 0.2 nor the 0.1 source decides, the case states only `htmlIncludes`.

`options.extensions` names extensions of `data/extensions.json` as above, and also standard extensions outside that table by the name an engine selects them with, such as `carve.listTable` or `carve.fencedRender.dot`. The runner registers such an extension as its whole standard bundle, with its document transforms, and with its renderers where `renderers` maps the name to `"standard"`. A renderer with host options, as `{ "carve.codeGroup": { "standard": { "mode": "aria" } } }`, takes the options of the clause the case cites.

`scripts/next2-readiness.mjs` replays the file in the section "Extensions" of its report, with pass, fail and unsupported per engine and extension. It counts toward Engine ready and is part of the per-case baseline. Any failing or unsupported extension case fails readiness. `node scripts/next2-readiness.mjs --extensions-only` replays only this file and fails on those cases too.

## Refused trees

Each entry has `id`, `clauses`, `reason`, `refusedBy` (`schema` when `data/ast-schema.json` refuses the tree, `reader` when only a reader check beyond the schema does) and `tree`. A 2.0 reader refuses every one, with `CarveTreeError`. A tree the reader refuses has `path`, the pointer of the node or field its reader check refuses (C2-A-167); an error that names that pointer, a field below it, or the node that holds a field it names agrees, as in `expected.refusal`.

## Reading it

An engine needs a JSON reader and a loop: for each entry, run the operation of its `kind` with its `options`, and compare with each field of `expected` the engine implements. Report the `id` of each entry that differs.
