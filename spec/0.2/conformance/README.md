# Conformance corpus of Carve 0.2

One corpus for every engine. Three plain JSON files, one schema (`schema.json`, JSON Schema 2020-12). Each file has `$schema`, `kind` and `description`, and one list.

| File | `kind` | List | Made by |
|---|---|---|---|
| `examples.json` | `examples` | `examples`: every example of the ten documents | generated by `scripts/spec2-conformance.mjs --write`; do not edit |
| `clause-cases.json` | `clause-cases` | `cases`: inputs a clause decides that no example holds | curated by hand |
| `refused-trees.json` | `refused-trees` | `trees`: trees a 2.0 reader refuses | generated from `trees/refused.json`; do not edit |

`npm run spec2:data` runs `node scripts/spec2-conformance.mjs --check`, which fails when a generated file is stale, when a file does not match the schema, when a clause case cites a clause no document defines, when its `why` is not text of the clause it names, when its expected children are not a valid tree, and when it repeats the input and options of an example.

## Examples

Each entry:

| Field | Value |
|---|---|
| `id` | the document stem and the example number, as `syntax-blocks-12` |
| `document`, `number` | the document file and the number the example has there |
| `section`, `clauses` | the heading of the section the example stands in, and the clause ids that section defines |
| `kind` | `render`: Carve input to HTML; `write`: Carve input to canonical Carve; `lint`: Carve input to the codes lint reports; `include`: an entry document and the files a resolver serves; `import`: HTML input to a tree and canonical Carve |
| `input` | the Carve input; absent for `import` |
| `html` | the HTML input of an `import` example |
| `files` | for `include`: each file the resolver serves under its name, which is also its id, as `{ "text": ... }` or as `{ "bytes": "61 FF" }` in hex |
| `options` | the options the example's flags set, by the names of `data/options.json` (see "Options"); `{}` for none |
| `expected.html` | the expected HTML |
| `expected.htmlIncludes` | where the example states its output in prose: a piece the HTML holds |
| `expected.tree` | the expected tree, positions included, where the tree gate holds one (`trees/`) |
| `expected.children` | for `import`: the children of the imported document, without positions |
| `expected.carve` | for `write` and `import`: the source the canonical writer gives, with its final line feed (C2-W-022) |
| `expected.diagnostics` | the codes of `data/lint-rules.json` on the line of the example that starts with `Reported:`; no code is taken from other prose. Not a complete list, except for `lint`, where it is what the example states |
| `status`, `reason` | `verified` or `unverified`, and why, as the conventions of the document define it |
| `note` | where the example states its input in prose (blocks Example 247) |

Comparing: HTML is compared byte for byte, and so is Carve source (`expected.carve`). A tree is compared under the equality of C2-A-162, or with positions where the engine claims C2-A-165. An include example is parsed with a resolver that serves exactly `files` and returns each name as its id (`includes.md`, conventions).

What the status means:

- `syntax-blocks`, `syntax-inline`, `html`, `writer`: *verified* is what the documents call *generated*, the output of the 0.1 reference engine for an input whose 0.2 rule equals 0.1 behavior; *unverified* output is written by hand from the clauses.
- `includes`: every example is unverified (`includes.md`, conventions). Its tree in `expected.tree` comes from the tree gate.
- `import-html`: *verified* means the reference importer at the commit the conventions name gives this tree and source.

An unverified example is still the expected result: where an engine differs, the clause decides.

## Clause cases

Each entry has `id` (`CC-nnn`), `clauses`, `why`, `summary`, `options`, `expected` and `from`, the engine case files it was merged from (`js:ID`, `php:ID`, `rs:ID`; empty for a case written from the clauses). `why` quotes the sentence that decides the case, as `C2-B-130: ...`; several quotes follow one another, and ` ... ` joins two pieces of one clause. `corrected`, where present, says what the engine files expected before the clause corrected it.

`kind` names the call the case runs (`tooling.md`, C2-T-005). An entry without `kind` is a render whose `expected` states both `html` and `children`, the children of the document without positions; that is the shape of every case up to CC-359.

| `kind` | Input | Call | What `expected` may state |
|---|---|---|---|
| `render` | `input` or `inputBytes`, `files` | `renderWithDiagnostics`, and `parse` for `children` | `html`, `children`, diagnostics |
| `parse` | `input` or `inputBytes`, `files` | `parseWithDiagnostics` | `children`, diagnostics |
| `lint` | `input` or `inputBytes`, `files` | `lint` | diagnostics |
| `format` | `input` or `inputBytes` | `formatWithDiagnostics` | `carve`, diagnostics |

`inputBytes` is the input as bytes in hex, for a source that is not well-formed UTF-8 (C2-B-218). `files` holds the files a resolver serves, as for an include example; a case with `files` is parsed with that resolver and one without `files` with none (see "Options").

### Diagnostics

`expected.diagnostics` lists entries of the record the call returns. An entry is a code, or an object with `code` and any of `line`, `column`, `endLine`, `endColumn`, `severity`, `channel`, `path` and `file`. `line` and `column` are the start of the entry's `range`, counted as `pos` counts them (C2-A-141): lines from 1 at each line feed, columns in code points from 1. They are counted in the file the entry names (`file`, C2-N-063) and in the input otherwise; the end is exclusive, as in `pos`. A field the object does not state is not compared.

`expected.diagnosticsComplete` set to `true` says the record holds the listed entries and no others; otherwise it holds at least them, in any order. `expected.notReported` lists codes the record must not hold: the near miss of a rule. `expected.suppressed` is the `suppressedDiagnostics` of the result (C2-T-024).

```json
{
  "kind": "lint",
  "input": "a **b** c\n",
  "options": {},
  "expected": {
    "diagnostics": [{ "code": "markdown-strong-double-star", "line": 1, "column": 3, "endLine": 1, "endColumn": 8, "channel": "lint" }],
    "notReported": ["markdown-italic-underline"]
  }
}
```

The check fails a code that `data/lint-rules.json` does not list or lists as obsolete or void, a `channel` or `severity` that differs from the catalog, a position outside the text it is counted in, and a code that is both expected and excluded.

## Options

`options` takes every option of `data/options.json` by its name, and `{}` is every default. The check fails a value that the row of the option does not allow, except a value the case expects to be refused (`expected.refusal` with `CarveOptionError` and the path of that option). Two options take host code, which JSON cannot hold, so a case names it: `extensions` lists standard extensions by their names in `data/extensions.json`, and `renderers` maps such a name to `"standard"`, its standard renderer. `includes` holds `file`, the id of the top-level document, and the lowered limits `depth` and `bytes`; a case with `files` is parsed with a resolver over them, and a case without `files` with no resolver. `rules` maps a code to `on` or `off`, and `platforms` lists platform names.

```json
{ "rules": { "djot-plus-bullet": "on", "bare-html-tag": "off" }, "platforms": ["github"], "extensions": ["carve.tabs"], "renderers": { "carve.tabs": "standard" } }
```

## Refused trees

Each entry has `id`, `clauses`, `reason`, `refusedBy` (`schema` when `data/ast-schema.json` refuses the tree, `reader` when only a reader check beyond the schema does) and `tree`. A 2.0 reader refuses every one.

## Reading it

An engine needs a JSON reader and a loop: for each entry, run the operation of its `kind` with its `options`, and compare with each field of `expected` the engine implements. Report the `id` of each entry that differs.
